# Шлюз ИИ-наставников

`AgentService` проверяет владельца сессии и доступность агента. `AgentRequestBuilder` формирует системный промпт, контекст и историю. `AgentGatewayPort` получает готовый запрос; `ProfileAgentGateway` выбирает профиль и вызывает адаптер протокола. Профиль общий для всех агентов и читается при запуске backend. Миграция V17 добавляет время изменения содержимого решения и индекс контекста, V18 — порядок сообщений в сессии; Flyway применяет их при запуске.

## Быстрый запуск

По умолчанию `AGENT_ACTIVE_PROFILE=mock`: сеть не используется, ответ явно обозначен как демонстрационный. Наличие ключа само по себе больше не включает провайдера. При обновлении существующего развёртывания обязательно укажите `anthropic` или `gemini`, если хотите сохранить реальные ответы.

Внешний совместимый API:

```dotenv
AGENT_ACTIVE_PROFILE=cloud
AGENT_CLOUD_BASE_URL=https://your-provider.example/v1
AGENT_CLOUD_MODEL=your-model-id
AGENT_CLOUD_API_KEY=your-secret
AGENT_FALLBACK_PROFILE=
```

Адрес должен указывать на корень API: адаптер добавляет `/chat/completions`. Поддерживается нестриминговый текстовый Chat Completions с `system`, `user`, `assistant` и строковым `choices[0].message.content`. Совместимость конкретной модели нужно проверить: название «OpenAI-compatible» не гарантирует поддержку всех параметров. Для эндпоинта с другим названием лимита задайте `AGENT_CLOUD_TOKEN_LIMIT_FIELD=max_completion_tokens` (по умолчанию `max_tokens`). Responses API, инструменты, изображения и streaming в этот контракт не входят.

Anthropic: `AGENT_ACTIVE_PROFILE=anthropic`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`. Gemini: `AGENT_ACTIVE_PROFILE=gemini`, `GEMINI_API_KEY`, `GEMINI_MODEL`. Выберите доступный вашему аккаунту идентификатор модели; дефолты проекта не гарантируют её доступность. Ключ Gemini передаётся заголовком `x-goog-api-key`, а не в URL.

Собственный сервер модели с тем же HTTP-контрактом:

```dotenv
AGENT_ACTIVE_PROFILE=local
AGENT_LOCAL_BASE_URL=http://localhost:8000/v1
AGENT_LOCAL_MODEL=your-served-model-name
AGENT_LOCAL_API_KEY=
AGENT_FALLBACK_PROFILE=
```

Пустой ключ означает отсутствие заголовка Authorization. Адрес `localhost` подходит для backend, запущенного непосредственно на машине сервера модели. Для backend в Docker Desktop и модели на хосте используйте `http://host.docker.internal:8000/v1`; для отдельного контейнера — его DNS-имя в общей Docker-сети. В Linux разрешение `host.docker.internal` при необходимости настраивается отдельно. GPU, модель и inference-сервер этим проектом не устанавливаются.

Корневой `.env` используется Docker Compose. После изменения параметров выполните `docker compose up -d --build backend frontend`, чтобы пересоздать сервисы с обновлёнными переменными. При запуске JAR/Gradle задайте переменные в окружении процесса: Spring автоматически не читает корневой `.env`.

## Дополнительные профили и лимиты

Дополнительный YAML можно подключить через `SPRING_CONFIG_ADDITIONAL_LOCATION=file:/absolute/path/agent-profiles.yml` (в контейнере предварительно смонтировать файл и передать эту переменную). Например:

```yaml
sbertrack:
  agent:
    active-profile: cloud-backup
    fallback-profile: ""
    profiles:
      cloud-backup:
        protocol: OPENAI_COMPATIBLE
        base-url: ${BACKUP_BASE_URL}
        api-key: ${BACKUP_API_KEY:}
        model: ${BACKUP_MODEL}
        connect-timeout-ms: 5000
        read-timeout-ms: 30000
        max-output-tokens: 1024
        max-attempts: 2
        retry-delay-ms: 500
        token-limit-field: max_tokens
```

Ключи храните в окружении или средствах управления секретами. Не включайте их в репозиторий, URL или параметры frontend. Неверный выбранный профиль, пустая модель/адрес или отсутствующий обязательный ключ останавливают запуск; невыбранные заготовки профилей могут оставаться пустыми. Перенаправления HTTP отключены.

Дефолты каждого профиля: соединение 5 секунд, чтение 30 секунд, 2 попытки, пауза 500 мс, ответ до 1024 токенов. Ограничение входа `AGENT_MAX_INPUT_CHARS=32000` измеряется в символах, а не токенах; `AGENT_MAX_HISTORY_MESSAGES=20` включает текущий запрос. Подбирайте оба лимита под контекст выбранной модели. Старые сообщения удаляются из передаваемой истории без изменения сохранённой переписки. Если системный промпт и текущий контекст уже не помещаются, API возвращает 400. Сообщение ограничено 8000 символами, список материалов — 20 строками по 1000 символов.

## Ошибки и резервный профиль

Повторяются только сетевые ошибки (в том числе таймаут/обрыв во время чтения тела ответа), HTTP 429, 500, 502, 503 и 504. Получение полного тела отделено от разбора JSON: некорректный JSON не считается сетевым сбоем. Прерывание потока останавливает обработку без повторов и перехода к резерву. После исчерпания попыток используется только явно заданный `AGENT_FALLBACK_PROFILE`. По умолчанию резерв отключён: self-hosted запрос самопроизвольно не уйдёт наружу. При включении резерва туда передаётся весь тот же запрос, включая историю и контекст. После сетевой ошибки провайдер мог уже обработать запрос: повторы могут тарифицироваться отдельно.

Ошибки авторизации, формата и пустой ответ не вызывают повтор или обход через другого провайдера. Пользователь получает 503 без внутренних подробностей. Оба новых сообщения записываются одной транзакцией только после успешного ответа. Чат показывает ошибку, восстанавливает введённый текст и повторно использует созданную сессию. Повтор после потери ответа уже на участке backend–браузер пока не идемпотентен.

Логи содержат имя профиля, модель, номер попытки, результат/HTTP-статус и длительность. Ключи, тексты запросов/ответов и тела ошибок провайдера шлюз не логирует. Не включайте HTTP wire/debug-логирование в рабочем окружении без отдельной фильтрации секретов.

Nginx ждёт API до 150 секунд, чтобы покрыть дефолтные попытки основного и резервного профилей. При увеличении таймаутов/числа попыток согласуйте бюджет ожидания с вашим reverse proxy. Ограничения частоты и общей стоимости запросов, очередь задач и потоковая выдача — отдельные следующие этапы.

## Контекст и доступ

Создание, чтение, поиск последней сессии и отправка доступны только активному студенту, владельцу сессии. Переданный чужой `studentId` отклоняется. Продолжать чат с отключённым агентом нельзя. При формировании запроса используется только активный мастер-промпт, принадлежащий этому агенту; иначе применяются базовые инструкции наставника.

Название, описание и ожидаемый результат опубликованного кейса берутся из БД. Поле `caseTitle` сохранено для обратной совместимости HTTP, но не используется. Запрос включает до пяти собственных сохранённых решений студента в этом кейсе, начиная с последних созданных или отредактированных. При одинаковом времени используется ID как стабильный дополнительный порядок. Изменение статуса, отзыв и рефлексия не повышают приоритет старого содержимого. Длина полей ограничена. Для старых записей V17 использует известное время отправки; у черновиков без исторической даты — 1970-01-01, поэтому они уступают датированным работам до следующего редактирования. Фактическое время старых правок восстановить невозможно. Артефакты из браузера передаются отдельно как пользовательские ссылки/подписи. Содержимое URL и файлов не загружается; RAG и анализ файлов не реализованы. Контекст помещается в пользовательское сообщение, а не в системные инструкции.

## Проверка

`./gradlew :backend:build` требует тестовую PostgreSQL с переменными `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`: интеграционные тесты используют seed-пользователя и создают тестовые сессии/пользователей. Используйте отдельную БД, не production. `cd frontend && npm test` и `npm run build` проверяют интерфейс.

`AgentGatewayTest` проверяет HTTP-контракты трёх протоколов, ключи, лимиты, повтор, резерв, таймаут и пустой ответ на локальном HTTP-сервере. `AgentRequestBuilderTest` проверяет контекст, промпт и историю. `AgentContextPersistenceTest` на PostgreSQL проверяет выбор последних работ, повторное редактирование, стабильный порядок и исключение чужих студентов/кейсов. Тесты шлюза отдельно проверяют таймаут после получения заголовков, резерв после исчерпания повторов, некорректный JSON и прерывание потока. `AgentControllerIntegrationTest` проверяет доступ и сохранение. `AgentCompatibleIntegrationTest` проходит полный путь от HTTP-контроллера через настоящий шлюз до тестового совместимого HTTP-сервера и БД. Frontend-тест проверяет восстановление черновика и повторную отправку.

Эти проверки не подтверждают качество реальной модели или доступность аккаунта провайдера. Для живой проверки выберите профиль, задайте модель/ключ, войдите студентом, отправьте два сообщения и перезагрузите чат; проверьте историю и запись `result=ok` в логах. Для self-hosted дополнительно нужны запущенная модель, совместимый chat template и оценка памяти/задержек на целевой машине.

Справочники протоколов: [Gemini generateContent](https://ai.google.dev/api/generate-content), [Anthropic Messages](https://platform.claude.com/docs/en/api/messages), [vLLM compatible server](https://docs.vllm.ai/en/latest/serving/openai_compatible_server/).

## Порядок сообщений и восстановление чата

Чат сначала восстанавливает последнюю сессию выбранного студента, агента и кейса. Пока запрос не завершён, отправка недоступна. Ошибка восстановления показывается отдельно с кнопкой «Повторить загрузку» и не считается отсутствием сессии. Устаревшие ответы загрузки или отправки при смене контекста игнорируются. После ошибки генерации черновик остаётся в той же созданной/восстановленной сессии.

V18 вводит положительный `sequence_number` с уникальностью внутри сессии. История читается по этому номеру, а не по времени; одинаковые timestamps не переставляют USER и AGENT. Для старых сообщений миграция использует время и стабильное правило разрешения совпадений (USER перед AGENT, затем ID). Реальный порядок нескольких исторических сообщений с одинаковым временем ранее не записывался и не может быть гарантированно восстановлен.

Новая пара записывается атомарно под короткой блокировкой строки сессии. Если история изменилась за время генерации, результат не сохраняется и API возвращает 409: пользователь повторяет вопрос, после чего backend строит запрос по обновлённой истории. Во время вызова модели транзакция с блокировкой не удерживается. Механизм действует через БД и не зависит от числа экземпляров backend. Конкурентный отклонённый запрос мог уже расходовать токены; это не механизм отмены оплаты или идемпотентности доставки.

`AgentMessageOrderingIntegrationTest` проверяет одинаковые времена, обратный порядок вставки и конкурентное добавление пар на PostgreSQL. `AgentControllerIntegrationTest` проверяет HTTP 409 без частичной записи и успешный повтор. Frontend-тесты проверяют ожидание истории, повтор её загрузки, смену агента и повтор сообщения после ошибки на обоих экранах чата.
