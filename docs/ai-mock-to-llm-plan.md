# Переход с моков на реальный ИИ через API

Дата: 2026-07-02

## Короткий вывод

План должен оставаться узким и практичным: сделать так, чтобы ИИ-наставники работали в демо, не ломая уже рабочие части системы.

Оптимальный scope:

- заменить только mock-генерацию ответа в `AgentGatewayPort`;
- оставить текущие `AgentService`, `AgentSession`, `MasterPrompt` и seed-хранилище;
- добавить fallback на mock;
- использовать один провайдер, сначала Mistral;
- не вводить новую сложную оркестрацию, пока текущий сценарий не стабилен.

### Метод интеграции

Для этого репозитория выбираем **HTTP client**, а не SDK.

Почему:

- в официальных Mistral docs есть official SDK для Python и TypeScript, а для Kotlin нет официального SDK;
- HTTP client дает минимальный scope и не добавляет лишних зависимостей;
- текущий backend на Spring Boot уже хорошо ложится на тонкий `WebClient` или `RestClient`;
- так проще сохранить текущую архитектуру и не затронуть рабочие модули.

Следствие:

- в первом релизе не тянем third-party Kotlin SDK;
- не строим отдельный integration layer сверх необходимого;
- делаем один аккуратный адаптер вокруг HTTP-вызова.

## Аудит исходного плана

### Что в плане хорошего

- Правильно выбран минимальный радиус изменений: сначала менять `agent`-контур, а не всю платформу.
- Верно выделены prompt templates и версионирование.
- Верно отмечены guardrails, fallback и logging.
- Правильно поставлен акцент на разные специализации наставников.

### Что в плане нужно усилить

- Не было явного разделения между:
  - источником данных,
  - сборкой контекста,
  - вызовом модели,
  - постобработкой ответа.
- Не хватало стратегии на случай недоступности API.
- Не был описан формат входного контекста для модели.
- Не был указан бюджет по токенам и длине ответа.
- Не был добавлен план тестирования качества ответа.
- Не было явного ограничения на scope: только Mistral, без мульти-провайдерной платформы.
- Не было короткого критерия готовности к демонстрации.

### Риски, если внедрять напрямую

- Модель начнет "разъезжаться" по стилю между агентами.
- Ответы могут становиться слишком длинными и дорогими.
- Без guardrails модель может начать подсказывать готовое решение вместо помощи.
- Без fallback demo будет ломаться при любой проблеме у провайдера.
- Если смешать storage и gateway в одном классе, дальнейшая миграция на БД или другой LLM станет дорогой.
- Если сразу пойти в универсальную LLM-платформу, интеграция начнет затрагивать рабочие элементы без необходимости.

## Отполированная версия плана

### Цель

Заменить deterministic mock-ответы на реальный LLM-backed наставник так, чтобы:

- студент получал полезные подсказки, а не готовое решение;
- модератор мог менять промпт без деплоя;
- backend оставался устойчивым к ошибкам внешнего API;
- demo можно было запускать бесплатно или почти бесплатно;
- остальная система работала без изменений.

### Шаг 1. Разделить ответственности

Оставить в проекте три разных слоя:

- `MockPlatformDataStore` - хранение seed-данных и runtime-состояния;
- `AgentService` - orchestration и бизнес-правила;
- `AgentGatewayPort` - единственная точка обращения к внешнему ИИ.

На этом шаге mock-реализацию gateway не удалять, а оставить как fallback.

### Шаг 2. Ввести один provider adapter

Сделать одну новую реализацию порта:

- `MistralAgentGatewayAdapter`

Пусть адаптер принимает уже собранный контекст и возвращает только текст ответа.
Никаких мульти-провайдерных абстракций на старте не нужно.

### Шаг 3. Вынести сборку prompt/context в отдельный builder

Собирать запрос к модели из явно типизированных кусочков:

- роль агента;
- специализация агента;
- active master prompt version;
- title и description кейса;
- история сообщений;
- список артефактов;
- ограничения поведения;
- формат ответа.

Рекомендуемый формат ответа:

- краткое резюме понимания задачи;
- 3-5 уточняющих или проверочных вопросов;
- 2-4 следующих шага;
- предупреждение, если данных недостаточно;
- короткий финальный safety line: "я не решаю задачу за тебя".

### Шаг 4. Добавить guardrails

Нужны системные ограничения, которые проверяются до вызова модели и после ответа:

- не генерировать финальное решение целиком;
- не придумывать факты;
- не выдавать уверенность без контекста;
- не выходить за лимит длины;
- не использовать персональные данные без необходимости;
- не ломать тон конкретного агента.

Практически это лучше делать в двух местах:

- в system prompt;
- в backend post-processing, где можно обрезать слишком длинный ответ и добавить безопасный retry.

Для первого релиза guardrails не должны превращать систему в отдельный policy engine. Достаточно:

- system prompt;
- базовая проверка длины;
- блокировка слишком рискованных ответов по простым правилам;
- fallback на mock при проблеме.

### Шаг 5. Добавить fallback режим

Если API недоступен, backend должен:

- вернуть короткий предсказуемый ответ;
- не падать с 500 на пользовательском сценарии;
- логировать ошибку провайдера;
- сохранять сессию, чтобы пользователь не потерял контекст.

Fallback можно сделать так:

- сначала пробуем реальный provider;
- если ошибка таймаута/429/5xx, идем в mock;
- если и mock сломался, возвращаем короткий статический safe response.

### Шаг 6. Ограничить стоимость и длину ответа

Надо заранее задать:

- max input size;
- max output tokens;
- температуру;
- число попыток retry;
- timeout на запрос;
- rate limit на пользователя или сессию.

Для demo этого достаточно на уровне конфига и одного общего лимита, без отдельной подсистемы квот.

Для demo это особенно важно: короткие ответы и малые контексты почти всегда лучше длинных и дорогих.

### Шаг 7. Сохранить воспроизводимость

Нужны поля для аудита:

- какой provider использовался;
- какая model version;
- какая версия master prompt;
- какой был входной контекст;
- была ли использована fallback-ветка.

Эти данные нужны для отладки, но их не обязательно выносить в отдельное хранилище на первом этапе.

Это позволит потом объяснять поведение системы и отлаживать качество.

### Шаг 8. Добавить тестовый контур

Минимальный набор тестов:

- unit-тесты на builder контекста;
- unit-тесты на routing по specialization;
- тесты на fallback при падении API;
- snapshot/golden tests для типовых вопросов;
- smoke test для одной сессии в UI.

Для первого релиза достаточно покрыть именно наставнический сценарий, а не всю платформу.

### Шаг 9. Подготовить rollout

Лучше внедрять поэтапно:

1. Один агент, например backend-architect.
2. Один сценарий, например `/agents/sessions/{id}/messages`.
3. Один провайдер.
4. Потом расширить на остальные специализации.

Так вы быстро получите working demo и не утонете в частичных поломках.

## Что не делаем в первом релизе

- не вводим мульти-провайдерную стратегию;
- не переписываем доменную модель;
- не меняем frontend-экраны без необходимости;
- не выносим промпты в отдельную админ-систему;
- не добавляем очереди, RAG и agent orchestration framework;
- не меняем рабочие модули вне `agent`-контура.

## Бесплатные или почти бесплатные API для вашей задачи

Ниже - кандидаты, которые реально подходят для demo и первых итераций.

| Провайдер | Почему подходит | Что важно учесть |
|---|---|---|
| Google Gemini API | Есть free tier, старт без оплаты, подходит для chat-style помощника, хороший вариант для быстрых прототипов | Free tier зависит от модели и лимитов; для отдельных моделей и больших объемов могут понадобиться billing/prepay |
| Mistral API | Есть Free mode без кредитной карты, удобен для evaluation/prototyping | Лимиты в free mode ограничены, нужен контроль длины ответов и частоты запросов |
| Hugging Face Serverless Inference API / Inference Providers | Удобно для тестов и демонстраций, можно быстро переключать модели | Бесплатные возможности и лимиты зависят от текущей политики/квот; для production обычно нужен pay-as-you-go |
| Groq API | Очень быстрый, OpenAI-compatible, хороший для демо и низкой задержки | В документации упор на developer plan и лимиты аккаунта; бесплатность и доступность лучше проверить в конкретном аккаунте перед выбором |

### Мой практический совет

- Для самого быстрого и дешевого demo: **Gemini API**.
- Для простого старта без карты: **Mistral Free mode**.
- Для экспериментов с разными open models: **Hugging Face Serverless Inference API**.
- Если важна скорость и совместимость с OpenAI SDK: **Groq** как запасной вариант после проверки аккаунта и лимитов.

### Что бы я выбрал для этой платформы

1. **Mistral** - если нужен старт без кредитки и быстрый прототип.
2. **Gemini** - если нужен более "универсальный" free-tier для демо с запасом по возможностям.
3. **Groq** - если хотите очень быстрые ответы и OpenAI-compatible интеграцию.
4. **Hugging Face** - если вам полезно сравнивать open-weight модели и не привязываться к одному vendor.

### Что не стоит брать как основной free вариант

- **OpenAI API** - это сильный продукт, но для этой задачи я бы не считал его базовым бесплатным вариантом для demo. Для экспериментов и исследований у OpenAI есть отдельные программы, но это уже не "free tier" в обычном смысле.

## Рекомендация по старту

Если цель - быстро показать работающий ИИ-наставник в этой платформе, я бы сделал так:

1. Оставил `AgentMockAdapter` как fallback.
2. Добавил один новый provider adapter.
3. Вынес сборку контекста в отдельный builder.
4. Подключил `Mistral` или `Gemini` для первого MVP.
5. Откатил все нестабильные ответы через fallback и лимиты.

Так вы получите работающую демку без рискованной полной замены моков сразу.

## Если идти через Mistral free mode

Для вашего кейса Mistral подходит как быстрый старт, потому что:

- free mode доступен без кредитной карты;
- можно быстро получить API key в Studio;
- есть chat completions, structured outputs, function calling и custom guardrails;
- модель `mistral-small-latest` подходит как первый практический выбор для демо.

Официальные ссылки:

- [Activate Studio and generate an API key](https://docs.mistral.ai/getting-started/quickstarts/studio/activate-and-generate-api-key)
- [Send your first API request](https://docs.mistral.ai/getting-started/quickstarts/developer/first-api-request)
- [Usage and limits](https://docs.mistral.ai/admin/billing-usage/usage-limits)
- [Known limitations](https://docs.mistral.ai/resources/known-limitations)
- [Chat endpoints](https://docs.mistral.ai/api/endpoint/chat)
- [Moderation & Guardrailing](https://docs.mistral.ai/studio-api/conversations/moderation)
- [Function Calling](https://docs.mistral.ai/studio-api/conversations/function-calling)
- [Structured Outputs](https://docs.mistral.ai/studio-api/conversations/structured-output/custom)

### Что учитывать в первую очередь

1. Free mode ограничен по usage и rate limits.
2. Лимиты зависят от организации, плана и модели, а при превышении возможен `429 Too Many Requests`.
3. Входной prompt и `max_tokens` должны помещаться в context window модели.
4. Ключ лучше хранить в секретах и ротировать, а не класть в репозиторий.
5. Для наставника лучше начинать с коротких ответов и небольшого контекста.
6. Для safety лучше использовать Custom Guardrails, а не надеяться только на текст prompt.
7. Если нужен более стабильный формат ответа, лучше использовать structured outputs или JSON schema mode.

### Практический стартовый набор

- `MISTRAL_API_KEY`
- `MISTRAL_MODEL=mistral-small-latest`
- timeout на запрос
- retry только на transient errors
- fallback на `AgentMockAdapter`
- ограничение длины ответа
- логирование latency, model name и типа ошибки
- HTTP client поверх `WebClient` или `RestClient`

### Почему не SDK

- SDK не нужен для текущего масштаба задачи.
- SDK для Kotlin у Mistral не является официальным вариантом.
- Внешняя обертка увеличит риск изменений вне `agent`-контура.
- HTTP client проще тестировать и проще заменить, если провайдер поменяется.

### Что значит "готово к использованию и демонстрации"

Интеграция считается готовой, если:

1. Студент открывает workspace и получает ответ от реального Mistral.
2. Если Mistral недоступен, ответ приходит через mock fallback.
3. Ответ остается в нужном стиле наставника и не раскрывает решение целиком.
4. Существующие экраны и сценарии платформы не ломаются.
5. В логах видно, какой provider был использован и сработал ли fallback.
6. Можно показать демо без ручной правки кода в момент презентации.

### Режим запуска для вашей платформы

1. Сначала подключить только одного агента, например `backend-architect`.
2. Потом расширить на остальные специализации.
3. Сначала использовать обычный chat completion, без tool calling.
4. Добавить guardrails сразу, если ответы идут к студентам напрямую.
5. После этого при необходимости включать structured outputs для более строгих сценариев.

### Мой вывод по Mistral

Для вашей демонстрации это хороший вариант первого провайдера.
Главные риски здесь не в модели, а в том, что:

- free mode может упреться в лимиты;
- без fallback демо будет ломаться;
- без короткого контекста ответы станут нестабильными по качеству;
- без guardrails модель может начать “помогать слишком сильно”.
